# TODO-001: 融合策略约束过强导致性能退步——Loop Engineering 的约束平衡问题

## 问题引出

> 这个项目就是一个 Loop Engineering，就是在模型的基础上给它铺了一条轨道，让模型在这几个轨道上高速运转。但这轨道不能给它太多的约束——给太多约束模型被限死，给太少模型又会产生幻觉不准确。需要找到一条既给了足够多的约束、但又没有那么多约束的路。这是一个很大的课题。

## 问题描述

### 实际发生了什么

fused_conv_sigmoid 算子（Conv2d + Sigmoid 融合）经历了两轮 workflow 迭代：

**第一轮（半融合方案，avg_speedup=4.56，24/24 全部达标）**：
- 两个独立 kernel：K1（Cube 做矩阵乘）算完 conv 后把结果写回 HBM 的临时空间 wsT，K2（Vector 做 sigmoid）再从 HBM 读 wsT
- 中间结果经 HBM 一次往返，但 K1 和 K2 各自内部流水线跑满，互不等待
- 性能很好，全部 case 达标

**第二轮（真融合方案，avg_speedup=2.87，24/24 也达标但整体慢了 59%）**：
- 用户指定 `--optimize-hint` 要求改为真融合：单个 kernel 内 Cube 算完 conv 后 L0C→UB 片上直传做 sigmoid，中间结果不回 HBM
- workflow 的 role 文件全部引导"必须真融合，假融合即使性能达标也不能退出"
- agent 严格执行，花了 7 轮实现真融合，又因 exit_decision 死循环空转了 8 轮
- 最终性能远不如第一轮的半融合方案

**核心问题不是"真融合一定差"**——换个场景（小 shape、计算密集型、HBM 带宽瓶颈）真融合完全可能更好。问题是 role 没有给 agent 一个"根据实际性能数据动态选择融合策略"的机制，不管数据怎样都强制真融合。

**但真融合方案（avg_speedup=2.87）远不如之前的半融合方案（avg_speedup=4.56）**：

| case | 半融合（K1+K2 两个 kernel） | 真融合（单 kernel） | 差距 |
|------|--------------------------|-------------------|------|
| case_3 | 9.7μs (6.95x) | 46.9μs (1.44x) | 半融合快 4.8 倍 |
| case_10 | 6.4μs (5.78x) | 11.3μs (3.28x) | 半融合快 1.8 倍 |
| case_14 | 16.7μs (3.26x) | 40.1μs (1.36x) | 半融合快 2.4 倍 |
| **整体** | **avg=4.56x** | **avg=2.87x** | **半融合整体快 59%** |

真融合虽然全部 case 达标（≥1.0），但性能被半融合碾压。

### 为什么真融合反而慢

半融合是两个独立 kernel，各自内部流水线满流水：
- K1（Cube）：全速做矩阵乘，不等任何 Vector
- K2（Vector）：全速做 sigmoid，不等任何 Cube
- 代价：中间结果 wsT 经 HBM 一次往返

真融合把 Cube 和 Vector 塞进一个 kernel，引入了 per-tile 同步开销：
- 每个 tile：Cube 算完 → 等 Cube 停 → FIX 搬 L0C→UB → 等搬完 → Vector 算 sigmoid → 等完 → 下一个 tile
- 省掉了 HBM 往返，但每个 tile 的串行等待累积起来更大
- 大 shape（tile 数多）时，同步开销 > 省掉的 HBM 搬运

## 当前 role 中关于融合的约束（问题来源）

### stage2（n1_stage2_first_impl.md）——首版实现

- "融合要真正减少数据搬运：不要只看是否合成一个 Kernel，要检查中间结果是否仍写入 GM/workspace；同 Kernel 不等于片上数据融合"
- design_rationale 必须有「融合算子方案」章节，写清楚"L0C→UB 片上直传 vs 写回 HBM 再读"
- **约束方向**：引导 agent 追求片上直传，暗示写回 HBM 是不好的

### stage3（n1_stage3_fix_and_optimize.md）——迭代修改

- 历史经验字段第 4 条：融合算子策略追踪（fusion_kernel_strategy），❌无效方向不要重复，✅有效方向要保持
- design_rationale 必须有「融合算子方案」章节，说明"本轮修改对融合的影响：是否改善了融合程度"
- **约束方向**：每轮修改都要改善融合程度，不鼓励保持或回退到半融合

### stage9（n4_stage9_tech_lead_guide.md）——Tech Lead 决策（最强约束）

- "真正的融合应该是：一个 @pl.jit kernel 进去原始数据，出来最终结果，中间零 HBM 读写"
- `exit_decision: true` = 真融合可退出，`false` = **假融合即使 speedup 达标也继续迭代**
- suggest_next P0 优先级："融合方向最高优先""融合方式的优化优先级高于一切"
- **约束方向**：性能达标+假融合 → 不准退出。agent 完全没有"保留半融合因为它更快"的选项

### stage10（n5_stage10_kerminal_report.md）——最终报告

- 要求区分"真融合/半融合/假融合"，如果最终方案是半融合要说明原因
- **约束方向**：暗示半融合是需要解释的"不理想结果"

### 约束链条总结

```
stage2 引导"片上直传好于写回HBM"
  → stage3 每轮要求"改善融合程度"
    → stage9 硬性规定"假融合不能退出、融合优先级高于一切"
      → agent 被锁死在"必须真融合"这条路上
        → 即使真融合性能更差也无法回退
```

所有 role 都在同一个方向上施加压力，没有任何一个 role 说"如果真融合性能不如半融合，可以保留半融合"。

## 底层原理：约束过强的危害

这是一个典型的 **Loop Engineering 约束平衡问题**：

### 约束太强（当前问题）

role 里写死了"融合方向最高优先""假融合即使达标也继续迭代""融合方式的优化优先级高于一切"。agent 被这些约束锁死，即使发现真融合性能更差也不敢回退到半融合——因为 role 说了"假融合不能退出"。

结果：agent 在一条已经证明次优的路上死磕，浪费 14 轮迭代（其中 8 轮是 exit_decision 死循环），最终产出一个性能远不如半融合的方案。

### 约束太少（另一个极端）

如果完全不约束融合方向，agent 可能：
- 直接用 torch 现成算子拼接（假融合/作弊），触发反作弊零分
- 每轮随机尝试不同方向，没有积累，性能震荡
- 不理解"融合"的核心价值，写出结构正确但性能差的代码

### 正确的平衡点

**不是"要不要融合"的二选一，而是"哪种融合策略在当前 case 下最优"的动态判断。**

## 初步解决方案

### 方案 A：先不融合，再考虑融合

1. 第一阶段（iter1-N）：不约束融合方向，让 agent 自由选择最优实现（可能是半融合、可能是真融合、可能是混合）
2. 达标后：记录当前方案的性能 baseline
3. 第二阶段（可选）：如果用户指定 `--optimize-hint "尝试真融合"`，在 baseline 基础上尝试真融合
4. 对比：如果真融合比 baseline 更好则采用，否则保留 baseline

好处：不会因为"必须真融合"的约束把一个本来 4.56x 的好方案拉到 2.87x。

### 方案 B：性能对比退出

修改 `exit_decision` 的判断逻辑——不只看"是不是真融合"，还看"是否比上一版更好"：
- 如果有 `--init-impl`（基线），对比真融合 vs 基线的 avg_speedup
- 真融合更好 → 采用真融合退出
- 真融合更差 → 提示用户"真融合性能退步 X%，建议保留半融合方案"
- 没有基线 → 只看绝对性能（当前逻辑）

### 方案 C：多轮融合不提升时请求人类指导

如果连续 N 轮（如 3 轮）融合方向的 avg_speedup 没有实质提升（delta < 5%），且 tech_lead 的 insights 里所有融合方向都标记为 ✅已验证 或 ❌已否决：
- 不自动继续迭代
- 暂停 workflow，输出当前状态报告，请求用户确认：
  - "当前真融合方案 avg=2.87x，是否满足需求？"
  - "是否尝试回退到半融合方案？"
  - "是否提供新的优化方向？"

### 方案 D：混合策略（最优但最复杂）

让 agent 实现动态路由：
- 小 shape（tile 数少）→ 真融合（同步开销小，省 HBM 收益大）
- 大 shape（tile 数多）→ 半融合（两个 kernel 各自满流水，吞吐更高）
- host 侧根据 input shape 自动选择路径

这需要 agent 同时维护两套 kernel，复杂度高，但理论上性能最优。

## 核心课题

> 在 Loop Engineering 中，如何设计约束使得：
> 1. agent 有足够的方向感（不会乱试、不会作弊）
> 2. agent 有足够的自由度（能根据实际数据调整策略、能回退、能承认"这条路走不通"）
> 3. 约束能随迭代动态调整（前期紧、后期松；性能提升时加强方向、性能停滞时放松约束允许探索）

这不是一个简单的参数调优问题，而是一个**人机协作的控制论问题**。
